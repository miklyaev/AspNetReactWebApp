# Предложения по развитию проекта (брокеры сообщений)

## Что это за проект

**Jira-клон** — монолитное full-stack приложение:
- **Backend**: ASP.NET Core 8, REST-контроллеры (`/api/*`), cookie-аутентификация, RBAC (Admin/Leader/Executor).
- **Data**: EF Core + PostgreSQL 16, доменная модель в отдельном проекте `JiraClone.Data` (Goal → Project → TaskItem → Comment/TimeEntry, иерархия Employee → Leader/Executor).
- **Frontend**: React 18 (CRA) + React Router + Reactstrap, общается с API через `client.js`.
- **Инфраструктура**: Docker Compose (db + web), GitHub Actions → ghcr.io.

**Ключевая особенность текущей архитектуры** — всё синхронно и монолитно:
- Контроллеры напрямую дёргают `IDbService` → `AppDbContext` (нет слоя приложения/доменных событий).
- Нет фоновых задач, нет очередей, нет realtime. Фронт обновляет данные только перезагрузкой/повторным запросом.
- В `README.dev.md` уже заявлена идея AI-помощника для декомпозиции задач при превышении `PlannedTime` — это естественная точка для очереди.

## Где брокер сообщений реально полезен (по убыванию ценности)

### 1. AI-декомпозиция задач (уже заложено в планах)
Сейчас при создании задачи с большим `PlannedTime` ничего не происходит. Правильный паттерн — **outbox + очередь**:
- Контроллер сохраняет задачу в БД и пишет событие `TaskCreated` в outbox-таблицу (в той же транзакции).
- Фоновый процесс публикует событие в брокер.
- Consumer-сервис (AI-помощник) получает задачу, делает декомпозицию и создаёт подзадачи через API/сервис.

Это снимает главную проблему: AI-вызов может занимать секунды-минуты и не должен блокировать HTTP-ответ. Очередь даёт ретраи и не теряет события при падении.

### 2. Realtime-уведомления (комментарии, смена статуса)
Сейчас комментарии и статусы видны только после ручного обновления. Через брокер можно:
- Публиковать `CommentAdded`, `TaskStatusChanged`, `TimeEntryAdded`.
- Подписчик (SignalR-хаб или отдельный notification-сервис) доставляет их в UI в реальном времени.

Это самый наглядный «вау-эффект» для пет-проекта и хорошо демонстрирует pub/sub.

### 3. Пересчёт агрегатов (Progress, TimeSpent)
`Goal.Progress` и `Project.Progress` — вычисляемые, но считаются на лету в запросах. При росте данных это станет узким местом. Вариант: при `TimeEntryAdded`/`TaskStatusChanged` публиковать событие, а consumer пересчитывает и кэширует агрегаты (или пишет в отдельную read-модель — CQRS).

### 4. Асинхронные уведомления по email/внутренние алерты
События `TaskAssigned`, `TaskOverdue` → consumer шлёт письма/пуш. Отделяет доставку от основного потока.

### 5. Аудит и аналитика
Публиковать все мутации в `audit`-топик, отдельный consumer пишет в аналитическое хранилище. Не трогает основной БД-контур.

## Какой брокер выбрать

| Брокер | Плюсы для этого проекта | Минусы |
|---|---|---|
| **RabbitMQ** | Классика, отличная документация, `MassTransit`/`EasyNetQ` для .NET, легко поднять в Docker | Нужен отдельный контейнер |
| **Redis Streams** | Уже часто есть в стеке, лёгкий, подходит и для кэша, и для pub/sub | Меньше гарантий, чем у RabbitMQ |
| **Kafka** | Мощно, но для пет-проекта избыточен | Тяжёлый, сложный в настройке |
| **Azure Service Bus / AWS SQS** | Управляемый, ноль инфраструктуры | Привязка к облаку |

**Рекомендация для этого проекта**: **RabbitMQ + MassTransit** (или RabbitMQ + `IHostedService`-consumer без сторонних библиотек, чтобы меньше зависимостей). Он идеально ложится на Docker Compose, а MassTransit даёт готовые outbox, ретраи и консьюмеры.

## Предлагаемый план внедрения (поэтапно)

1. **Фундамент**: добавить `rabbitmq` в `docker-compose.yml`; подключить `MassTransit.RabbitMQ`; зарегистрировать шину в `Program.cs`.
2. **Outbox-паттерн**: таблица `OutboxMessage` + фоновый публикатор (MassTransit умеет это из коробки). Это гарантирует, что событие не потеряется, если брокер недоступен.
3. **Первый сценарий — AI-декомпозиция**: событие `TaskCreated` → consumer вызывает AI → создаёт подзадачи. Это закрывает заявленную в README фичу и сразу оправдывает введение брокера.
4. **Второй сценарий — realtime**: `CommentAdded`/`TaskStatusChanged` → SignalR-хаб → обновление UI без перезагрузки.
5. **Опционально**: пересчёт агрегатов и аудит-топик.

## Важные замечания по текущему коду (не про брокер, но пригодится)

- `DbService` — это по сути «толстый репозиторий» на 226 строк, контроллеры дублируют валидацию (проверка проекта/исполнителя повторяется в `TasksController`, `TimeEntriesController`). Перед введением событий стоит выделить слой приложения/сервисов, чтобы события публиковались в одном месте, а не в каждом контроллере.
- События логичнее публиковать после `SaveChangesAsync` в `DbService`/сервисном слое, а не в контроллерах — иначе легко пропустить событие при добавлении нового эндпоинта.
